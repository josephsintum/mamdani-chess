## Launch hardening: limits per IP

Found while load-testing on 2026-10-04 (`tools/loadgen`). Anyone can open as many live streams as they like, and each holds about 49 KB of server memory, so 10,000 streams is about 0.5 GB. The spec's abuse rules only cap reactions and body size. Before the public launch (milestone 07):

- Cap open streams per client IP (around 20; a household or office shares an IP, so not 1), answering 429 past the cap.
- Rate-limit API requests per IP (game creation especially: each game is a goroutine and about 6 KB).
- Behind Railway's proxy, take the client IP from `X-Forwarded-For` only from the proxy, not from any caller.
- Rerun `tools/loadgen` to check the caps don't trip real use: one player with a few tabs, a classroom on one IP.

## Launch check: HTTP/2

Found while watching agent-played games on 2026-10-04. Each open game tab holds one SSE stream for good, and over plain HTTP/1.1 a browser allows only 6 connections per host, shared by all tabs. With 6 game tabs open on one host, every other request from those tabs (piece SVGs, API calls) queues forever: the board draws without pieces and moves never send. Locally, `http://localhost:5173` hits this. In production, HTTPS lets browsers use HTTP/2, which multiplexes every tab over one connection, so the limit disappears, but only if HTTP/2 actually reaches the browser. In the Railway smoke test (milestone 07):

- Confirm the public URL serves HTTP/2: `curl -sI --http2 https://<domain>/ | head -1` shows `HTTP/2`, and the browser's Network panel shows protocol `h2` for `/api/games/*/stream`.
- Open 8 or more game tabs at once on the public URL and check that every board draws its pieces and moves still go through.
- If Railway's edge or the Go server ever fall back to HTTP/1.1, keep live updates working by capping streams per browser (one shared stream across tabs, or close the stream in hidden tabs) before launch.

## Observability and findings from the agent-played games

On 2026-10-04, 30 agents played games against each other through two separate headless browsers per game, in instant mode, with a third browser watching (20 complete games, 4,205 moves). Nothing failed:
- the server logged no errors, no panics and no 4xx or 5xx responses except 404s from tabs left open across a server restart;
- no browser logged a console error, warning or page exception;
- a move took 0.12 ms at the median and 2.1 ms at worst.

The run showed what the logs can't tell us. Every result had to come from the agents, not the server. Where each gap lands:

**Milestone 05 (Real games):**
- **One log line per game event:** created, Black joined, ended (reason, winner, number of moves), evicted, and (with persistence) restored after a restart or lost. Clocks, timeouts and forfeits add events of their own, so they belong in the same place. Log these at INFO.
- **A restart loses every game.** Two open tabs got 404 after a restart during the run. Saving games fixes this; check that a restored game's open tabs reconnect without a reload.
- **Clearer check status.** "Black to move — check!" doesn't say who is in check, and two agents read it as their own king. Name the side, e.g. "Black to move — Black is in check" or "Your move — you're in check".

**Milestone 07 (Launch):**
- **JSON log output.** Already in progress: `LOG_FORMAT=json` in the production image, so the host's log search can filter on fields.
- **Moves at DEBUG.** One INFO line per request meant 4,205 move lines for 20 games. Keep game events at INFO and move requests at DEBUG.
- **A request ID and the client IP** (from `X-Forwarded-For`, trusted only from Railway's proxy, as for the per-IP limits) on every request line.
- **Refusals logged at INFO with the reason** (illegal move, stale `seq`, wrong turn), so a confused player's report can be traced.

**For the rules doc's "Watch in test games":** potholes swung many games. Queens and rooks fell in the first few rolls, and many decisive results came from falls rather than play. The players were language models, so treat this as a prompt for the playtest with friends, not a verdict.

**Not covered by the run, so cover it elsewhere:** the server's refusal paths (the test harness only sent moves the board showed as legal), reconnecting in the middle of a game, and spectators who join late.

## Leaderboards: open questions

Leaderboards were added on 2026-10-04 as an idea. They change two things the spec lists as out of scope: accounts and ratings. They need a short design pass before a plan, answering:

1. **Who is on the board?** Guests are a browser cookie, so clearing cookies or switching phones makes a new player. Options: keep guests and accept that, let a guest "claim" their name with a passkey or email link, or require sign-in only for the leaderboard.
2. **What is ranked?** A skill rating (Elo or Glicko from wins and losses), plain win counts, or fun pothole stats such as most pieces saved by the Mamdani, most pieces lost to potholes, or luckiest rolls. The fun stats need no accounts and fit "fun to watch".
3. **Which games count?** Only quick match, or friend games too? Friend games are easy to farm by playing yourself in two browsers.
4. **When?** It needs saved games (milestone 05). Before or after the public launch (milestone 07)?

## Carried forward to later plans

- **The frontend is Svelte 5 (5.57) on SvelteKit 3 (3.0).** Svelte and SvelteKit are separate packages with separate version numbers. SvelteKit 3 changes the setup:
  - There is no `svelte.config.js`; config lives in `vite.config.ts`.
  - `$lib` is gone; use `#lib/…` imports instead.
  - `tsconfig.json` extends `$app/tsconfig`.
  - TypeScript stays on 6.x.
  - Node must be 22.17 or newer.

  Plan 01 sets this up, and every frontend plan must follow it.
- **The honk demo from Plan 01 is throwaway.** Plan 03 deletes it.
- **The concurrency model stays as spec §2 says:** one goroutine per game that owns its state, with commands over a channel. It serialises moves with three timer types (clock, dice pause, disconnect forfeit) without lock or stale-timer bugs.
- **Game lifecycle (plan [2026-10-04-go-server-improvements](2026-10-04-go-server-improvements.md)).** A game stops when a panic retires it or after a quiet day once over or unwatched; stopped games answer 404. Milestone 05's timers go in the same `select` in `game.loop`, and its tests can use `testing/synctest` instead of the spec's `Clock` interface. Persistence must reload stopped-but-unfinished games from SQLite on demand.
- **Rules interpretations made in Plan 02,** listed under "Interpretations made here" in that plan:
  - an "exposes" re-roll ignores the hole,
  - the checkmate re-roll covers any result of the roll,
  - with the Mamdani on the board, a king and one minor piece can still mate.

  If the rules doc rules otherwise, change the pinned test first.
- **House rules are deferred.** There is no `Settings` struct and no House rules panel until test games show a need (live doc, "Watch in test games").
- **Mamdani art is a launch blocker.** The photo on the canvas is a placeholder; Plan 07 must not ship without art we have rights to.
